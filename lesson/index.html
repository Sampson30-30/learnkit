Version control with Git and GitHub

A first lesson of about 40 minutes. By the end you can explain what version control is, follow the everyday routine, and recover when two people change the same thing.

Where are you starting from?
Part 1

Why keep a history?

Without version control, history lives in file names. Step through this story and see how it ends.

You write the first draft.
You make a copy before a big edit, just in case.
A colleague sends changes by email. You merge them by hand.
Someone edits the wrong copy. Nobody can say which has the latest figures.

Version control replaces that with one project and a full history of every change: who made it, when, and why.

Every saved change can be looked at, compared and undone. Mistakes stop being scary.

Several people can work on the same project at the same time, then bring their work together.

Each change carries a short message. Months later you can still see what you were thinking.
Part 2

The words you will hear

Git is the tool that tracks changes on your computer. GitHub is a website that stores a shared copy and helps people work together on it. Search the list, or jump to a letter.

Repository
A project folder together with its whole history. Often shortened to “repo”.
Commit
A saved snapshot of your changes, with a short message saying what changed and why.
Branch
A separate line of work. You can change things on a branch without touching the main one.
Merge
Bringing the changes from one branch into another.
Clone
Making a copy of a project from GitHub onto your own computer.
Push
Sending your commits from your computer up to GitHub.
Pull
Bringing other people's new commits from GitHub down to your computer.
Pull request
A request on GitHub to merge your branch, where others can review and discuss it first.
Conflict
What happens when two people change the same lines. Git asks you to choose what stays.
Part 3

Where your work travels

Your work passes through four places. Choose each numbered point to see what it is.

The folder you work in. Edit here as normal. Git notices what has changed but saves nothing yet.
A waiting room. You choose which changes go into the next snapshot, so one commit can be about one thing.
Every commit you have made, kept on your computer. You can work here without any internet.
The shared copy. Pushing sends your commits here so teammates can see them.

A project also holds a few standard files. Open the folders to see what each is for.

  • my-project
    • README.md: says what the project is and how to use it
    • .gitignore: files Git should never track, such as passwords
    • .git: the hidden history. Never edit it by hand
    • src
      • The project's own files
Part 4

The everyday routine

Most days you repeat the same four steps. Use Next to move through them.

Change your files as normal. Check what Git has noticed:

git status

Choose which changes go in the next snapshot.

git add report.md

Save the snapshot with a message that says why, not just what.

git commit -m "Correct the enrolment figures for autumn"

Send your commits to GitHub so others can see them.

git push

Part 5

Working side by side with branches

A branch lets you try something without risk to the main line of work. When it is ready, you open a pull request so others can review it before it is merged.

Not sure what to do next? Answer the questions and follow your route.

  • Is the change small and safe?
    • Is anyone else working on the same files?
      • Commit on the main branch
      • Make a branch and open a pull request
    • Make a branch and open a pull request

HEAD is just Git's bookmark for “where I am now”. It points at the commit you are working from.
  1. Install Git from git-scm.com, or install GitHub Desktop if you prefer buttons to commands.
  2. Create a free account on GitHub.
  3. Tell Git who you are, once: 
    git config --global user.name "Your Name"
git config --global user.email "you@example.com"
  4. Copy a project to your computer: 
    git clone https://github.com/your-name/your-project.git
Part 6

When two people change the same thing

Sooner or later it happens. Make the choices and see where they lead.

Activity 4: a conflict on Friday afternoon

You try to merge your branch. Git says: CONFLICT in timetable.md. A teammate changed the same line as you. What do you do?

  • Open the file and look at what Git marked
  • Delete your teammate's version and push yours

The file shows your lines and your teammate's lines between markers. Git cannot decide which is right, because only people know what the timetable should say.

  • Ask your teammate what they meant, then combine both
  • Keep yours and hope for the best

You agree the right wording, remove the markers, stage the file and commit. The history shows both changes and the decision. Nothing was lost.

Your version is kept, but it undoes your teammate's correction to the room number. Nobody notices until Monday. A short chat would have saved the day.

Your teammate's work is wiped from the shared copy. They have to rebuild it, and trust takes longer to rebuild. Never overwrite someone else's work to make an error go away.
Part 7

What GitHub adds

GitHub is more than a place to store a copy. Explore each part.

A to-do list for the project. Anyone can report a problem or suggest an idea, and discuss it in one place.
Propose a change, show exactly what differs, and gather review comments before anything is merged.
Automatic checks that run each time someone pushes, such as running tests, so mistakes are caught early.
A simple board to plan work and see what is waiting, in progress or done.
The front page of a project. It explains what the project is for and how to get started.
Named, dated versions of the project that people can download.

Teaching Claude your routines with skills

A lesson of about 35 minutes. By the end you can explain what a skill is, say where it is saved, write a description that gets it used, and choose between a skill and the other ways of guiding Claude.

About this page

What this is. A short sample lesson built only from LearnKit blocks. It shows how the blocks work together in a real course. The subject is skills in Claude Code, but the point is the blocks.

What you can do here

  • Work through the lesson from top to bottom, as a learner would.
  • Watch the bar at the top fill as you finish the five activities.
  • Change the “Look” at the top to see the same lesson in each style.
  • Ask Claude for any block by name, such as “add an lk-sort here”.
You do not need to know any code. Where the lesson shows a file or a command, you can read it as a plain instruction. Claude Code changes quickly, so its own documentation has the last word on details.

Where are you starting from?
Part 1

Why teach Claude a routine?

Claude starts each new conversation knowing nothing about how you like things done. Compare the same Monday morning with and without a skill.

Write my weekly update.
Happy to. What format should it be in, and who is it for?
Three parts: done, next and blocked. Short, plain English, for my manager.
Here is your update.
A week later: write my weekly update.
Happy to. What format should it be in, and who is it for?

Claude does not carry last week’s explanation into a new conversation. Unless it is written down where Claude can find it, you explain it again every time.

/weekly-update
Here is your weekly update, in your usual three parts: done, next and blocked.

The format lives in the skill, so you wrote it once. Typing the skill’s name runs it.

Can you do my status summary for this week?
Here is your weekly update, in your usual three parts.

You did not say the skill’s name. Claude matched your request to its description and used it anyway.

A skill is a saved set of instructions for one kind of job. Claude reads it only when it is needed, so it costs nothing the rest of the time.

Part 2

What is inside a skill

A skill is a folder with one file in it, called SKILL.md. Choose each numbered point to see what that part does.

The two lines of dashes fence off a small settings block at the top. Everything between them is information about the skill. Everything after is the skill itself.
What you type to run the skill, after a slash. This one is run with /weekly-update. If you leave it out, the folder’s name is used.
The most important line. Claude reads the descriptions of all your skills to decide which one fits your request. It says what the skill does and when to use it.
Plain sentences, written as you would brief a new colleague. Claude reads them only when the skill is used.
A skill can point at more files in its folder, such as a template. Claude opens them only when it needs them, so long reference material costs little.

Open the folders to see how it sits on disk.

  • weekly-update
    • SKILL.md: the name, description and instructions
    • template.md: an optional extra, read only when needed
    • scripts: optional small programs the skill can run
Part 3

Where a skill is saved decides who gets it

The folder you save a skill in sets who can use it. The ~ means your own home folder.

Saved in ~/.claude/skills/. It follows you into every project on your computer, and nobody else gets it.

Saved in a .claude/skills/ folder inside one project. It belongs to that project, and everyone who works on it gets it when the project is shared.

Arrives inside a plugin, which is a bundle someone made. You run it with the plugin’s name in front, such as /toolkit:review.

Activity 1: who gets it?

  • Your own checklist for tidying notes, wanted in everything you do
  • A shortcut for your personal style of email, used on every project
  • The release checklist for this one project, saved with its files
  • The way this team names files, which every new teammate should get automatically
  • A skill that arrived when you switched on a team toolkit
  • A skill you run as /toolkit:review, with the toolkit’s name in front
Part 4

The description is the trigger

Claude does not read every skill in full. It reads each description and decides from that alone. A vague description means the skill is never picked, however good the instructions are.

A good description says what the skill does and when to use it, using words you would really say.

Activity 2: which description gets the skill used?

You often ask, “Can you put together my status summary?” Here are three descriptions.

  • A: Helps with work stuff.
  • B: Writes my weekly update in three short parts. Use when I ask for a weekly update or a status summary.
  • C: weekly-update
Too vague. “Work stuff” matches everything and nothing, so Claude has no reason to pick this skill for a status summary.
It says what the skill does and the words you would use to ask for it, so a request for a status summary finds it.
This only repeats the name. Claude learns nothing about what the skill does or when to use it.

Write the description for Claude, as an answer to “when should I use this?”

The skill turns rough notes into clear actions with an owner for each. Here are three descriptions.

  • A: Use whenever the user asks anything about writing.
  • B: Turns rough meeting notes into a list of actions with an owner for each. Use after a meeting, or when I paste notes.
  • C: Use only when I type exactly /meeting-notes and nothing else.
Too broad. It would be picked for emails, essays and everything else, and get in the way.
Clear about the job, and it names the moments when it applies.
Typing the name would still work, but Claude would never pick the skill itself, because the description tells it not to.

Aim for specific, not broad and not tiny. If a skill is picked at the wrong times, narrow the description. If it is never picked, add the words people really use.

The skill checks a course page for broken links and unclear headings. Here are three descriptions.

  • A: Checks a course page for broken links and unclear headings. Use when I ask to review, proofread or check a course page before it goes live.
  • B: A really useful skill that I built last term.
  • C: Checks things.
It says what is checked and lists the ways you might ask, including “review”, “proofread” and “check”.
It describes how you feel about the skill, not what it does or when to use it.
Too short to match anything. Claude cannot tell this from any other checking job.

A few extra words of when-to-use cost nothing and make the skill far more likely to be found.
Part 5

Who presses the button?

By default, both you and Claude can start a skill. Two settings in the top block change that. You rarely need either, but the first one matters a great deal for anything risky.

Activity 3: who can start it?

Who can start a skill
SettingYou, by typing its nameClaude, by itself
Nothing set
disable-model-invocation: true
user-invocable: false
  • Nothing set suits everyday routines, such as the weekly update.
  • Only you suits anything with side effects, such as sending or publishing.
  • Only Claude suits background knowledge, such as house rules it should always know.
If the skill sends, publishes, deletes or spends anything, make it start only when you type its name. You decide when, not Claude.
Part 6

Skill, CLAUDE.md, hook or helper?

A skill is one of four ways to guide Claude. Choosing the right one is the real skill. Answer the questions and follow your route.

  • Must it happen automatically, every time, with no thinking needed?
    • A hook: a setting that runs a command at set moments, such as after every file is changed
    • Is it a rule or fact Claude needs in every conversation?
      • CLAUDE.md: a file Claude reads at the start of every conversation
      • Is it a routine with steps, or a how-to needed only sometimes?
        • A skill: read only when the job comes up
        • Is it a big side job whose working would clutter your chat?
          • A helper (subagent): a separate Claude that does the digging and reports back
          • Just ask in the chat

Activity 4: you keep pasting the same instructions

Every month you paste six lines into the chat that say how your team lays out the monthly report. You are tired of it. What do you do?

  • Save it as a skill
  • Put it in CLAUDE.md
  • Keep a note and carry on pasting

You write the six lines into a skill with a clear description. It works. A teammate asks whether they can have it too. Where do you save it so they get it?

  • In the project’s own skills folder, shared with the project
  • In your personal folder, and email them the file

Everyone on the project gets the skill when they get the project. The layout loads only in the month you write the report, so it never crowds out other work. When the layout changes, you change one file.

Your teammate saves their copy in their own folder. When you change the layout next quarter, their copy stays as it was. Soon two versions of the report are going round.

It works, but CLAUDE.md is read at the start of every conversation. The report layout now sits in view while you fix a typo or answer an email. It belongs in a skill, which loads only when the job comes up.

Pasting works until you forget a line or paste last year’s version. Anything you explain more than twice is worth saving once, where Claude can find it.
Part 7

Make your first skill

You can write the file yourself, or describe the routine to Claude and ask it to make the skill for you. Either way, these are the four steps.

Pick one routine you have explained at least twice. Small and specific beats big and clever.

Make a folder named after the skill, inside your personal skills folder.

~/.claude/skills/weekly-update/

Inside it, add a file called SKILL.md. Start with the name and description, then the instructions in plain sentences.

---
name: weekly-update
description: Writes my weekly update. Use when I ask for a status summary.
---
Write the update in three short parts: done, next, blocked.
Keep it under 150 words and avoid jargon.

In Claude Code, type /weekly-update. Then ask in your own words and see whether Claude picks it. If it does not, improve the description. If the skill does not appear at all, start a new conversation.

  • Write it as you would brief a new colleague on their first day.
  • Say what to do, not the story of why. Once a skill is used, its words stay in the conversation.
  • Keep SKILL.md short. Move long reference material into a second file and point to it.
  • Test with a request in your own words, not the skill’s name.

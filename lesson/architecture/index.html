How a project fits together

A lesson of about 30 minutes for anyone building software with Claude Code. By the end you can read a project as layers, judge how far a change will spread, and know what to ask before anything is added.

About this page

What this is. A second sample lesson built only from LearnKit blocks. It uses LearnKit itself as the worked example, so every number in it is real.

What you can do here

  • Work through it from top to bottom, as a learner would.
  • Watch the bar at the top fill as you finish the five activities.
  • Change the “Look” at the top. The page is itself an example of the idea it teaches.
  • Take the questions in Part 7 and use them with your own project.
Claude Code can add features faster than you can read them. This lesson is about keeping a map, so you stay in charge of the shape of what gets built.

Where are you starting from?
Part 1

A project is layers, not a list

A folder of files looks flat. It is not. Each file sits in a layer, and a file only knows about the layers below it. Choose each numbered point to see what the layer does. The numbers are from LearnKit.

The page chooses what to show and writes the content. It uses the pieces below but contains none of their working. If a page breaks, only that page breaks.
One short file that loads everything, so a page needs a single line. It decides what exists but does no work itself.
Each building block has its own file: a quiz, tabs, a table. Each one does one job and borrows from the layer below.
Shared code every component stands on. All 31 component files import base.js. Change it and 31 things change.
Colours, fonts and spacing live in one stylesheet and one theme, never inside a component. A theme changes the look and cannot change what anything does.
Part 2

Reading a file by its imports

Every file opens with a list of what it borrows. That list is a free summary of where the file sits. Step through it with src/lk-quiz.js.

Pick a file in the middle layer. Do not read the whole thing. Read only the first lines.

import { LkElement, define } from './core/base.js';
import { clamp } from './core/utils.js';
import { parseQuiz, scoreQuestion, scoreQuiz, shuffle } from './core/quiz.js';

Each line says: I borrow these things from that file. The quiz borrows the shared blueprint for every component, a small helper, and its own scoring rules.

Every path points into core/, which is the layer below. Nothing points up. That is how you know the layering is healthy.

Open core/base.js. It imports almost nothing. You have reached the bottom, and you know what everything above stands on.

  1. lesson/index.html, the page
  2. src/index.js, the front door
  3. src/lk-quiz.js, a component
  4. src/core/base.js, the base layer
Part 3

Three habits that keep a project healthy

Each one is a way of keeping concerns apart. Each has a real example from LearnKit.

Before adding something, find out whether it already exists.

When lk-sort was added, it needed dragging. lk-order already dragged, so the dragging code was lifted into one shared file, core/drag.js, and both components borrow it. The same change fixed dragging on touch screens for both.

The trap: copy the dragging code into the new component. Now there are two copies. Every later fix has to be made twice, and one is always forgotten.

Never style a component on its own. Style the system.

The main colour is written once per theme and read in 49 places in the stylesheet. Components create their buttons by giving them the class lk-button, instead of making their own. To change every button, you change one rule.

The trap: colour one component directly. It now ignores every theme, so switching the look leaves one odd piece behind.

Each layer does one thing and does not reach into another.

The quiz's scoring rules sit in core/quiz.js, apart from the code that draws the quiz. That is why the scoring can be tested without a browser, and why a theme can never alter a score.

The trap: mix the rules and the drawing together. Then you cannot change one without risking the other.
Part 4

Blast radius

The blast radius of a change is how much else it can affect. The layers tell you in advance. The lower the file, the wider the radius.

Activity 2: how far does it spread?

  • Fix a word in one lesson page
  • Change the scoring rules in core/quiz.js (only the quiz uses it)
  • Edit core/base.js (all 31 components use it)
  • Change the main colour in a theme (used in 49 places)
  • Change a helper in core/utils.js (11 components use it)

A large radius is not forbidden. It is a reason to slow down, check what depends on it, and run the tests. A small radius is a reason to relax.

Activity 3: a request lands

You are happy with the quiz, but its Next button looks dull. You ask Claude Code to make it orange. What do you do next?

  • Let it make the change in the quiz file
  • Ask it first where buttons are styled, and how many things share that style

The quiz button is orange. Every other button is not. Then you change the theme, and the orange button ignores it. Now there is one place that always needs special handling, and nobody remembers why.

Claude reports that buttons get their look from one shared style, lk-button, used by many components. The quiz button is not special. Now you can decide on purpose.

  • Change the shared button style, or the theme colour, so it is consistent
  • Add a clearly named variant for orange buttons, and use it only where needed

Every button across every component follows. You checked the blast radius first, so you know exactly what changed, and the next theme still works.

Only the quiz button is orange, and it is a named option in the shared styles, not a one-off. The exception is visible, reusable and themeable.
Part 5

Where does the bug live?

When something looks or works wrongly, ask one question first: which layer is it in? A bug belongs to a layer, not to a file. Three questions cover most of them.

The words, the answers, the order. Fix it on the page. Nothing else needs to change.

It does the wrong thing: a score adds up wrongly, a key does nothing. Fix it in the component or the base layer. Every page that uses it is fixed at once.

Colour, size, spacing. Fix it in the shared styles or the theme. Every piece that uses them follows.

Activity 4: sort the bugs

  • A typo in a lesson
  • A quiz answer marked correct by mistake
  • The quiz adds up the score wrongly
  • Tabs ignore the arrow keys
  • Every button is the wrong blue
  • Text is too small in the dark look
 If every page was built on its own, each one has its own copy of every button and every rule. The same bug now lives in many places, and each copy differs slightly, so fixing one tells you nothing about the rest. Layers turn “find the file” into “find the layer”.
Part 6

Why keeping things pays off

One developer’s account of building the same kind of software more than once. Step through it.

Each page was built on its own, so each button was made again with its own style. The look was left until last, and that seemed fine.
Standalone pages were joined into one product. When an AI was asked to do the joining, it produced small variations everywhere, and debugging got harder.
Each component and each style was kept and reused. Every new project started with the last project’s pieces.
Everything had to be learned and made for the first time.
The components and the lessons from the CRM were used again. Building got faster each time.

Keep one caution in mind. Keep what you use a second time, not everything you ever make. A library only helps while it stays small enough to know.

Part 7

Before Claude adds anything

Claude Code is quick to add things and does not always look sideways first. These questions put you in charge of where new work lands. Start with this decision.

  • Does something that already exists do most of this?
    • Reuse or extend it. Ask Claude to show you the existing file first
    • Will two or more parts need it?
      • Put it in the base layer and import it
      • Build it inside the one component that needs it

Then use these questions in your own project. Open each one for the exact words to give Claude.

Before you add anything, search this project for existing code that
does something similar. Tell me what you found and whether we should
reuse or extend it instead of writing something new.
List every file that imports the file you are about to change. Tell
me how many there are, and which ones could behave differently.
Do not add colours, fonts or sizes directly to a component. Find
where the shared styles live and use those. If a style is missing,
add it there and tell me.
Read this project and write ARCHITECTURE.md: the layers, one line per
folder, and which layer each file belongs to. Flag anything where a
lower layer imports from a higher one.
 Ask for that ARCHITECTURE.md file and keep it up to date. Every new Claude session then starts from the same map, and so do you.
